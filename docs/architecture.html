Confidential code & IaC scanning:
operator-excluded, open-source architecture on GCP

A vulnerability-scanning service where third-party vendor code and infrastructure-as-code are decrypted, analyzed by an open-weight LLM and deterministic scanners, and re-encrypted — exclusively inside a hardware trusted-execution environment that the service operator provably cannot access. Published as the open-source project Confidential Assurance Framework (CAF) so anyone can rebuild the measured image and check it.

TEE: Confidential Space · Intel TDX + H100 today → Blackwell CC (NVLink-encrypted) next Model: Nemotron 3 Ultra (OpenMDW) target · Foundation-sec-8B sidecar · vLLM Attestation: EAT / RATS · Google Cloud Attestation · Intel Tiber (optional)
01

Trust model — who trusts what

The product being sold is not a scan; it is a proof. Every design decision below serves one claim: vendor plaintext exists only inside attested hardware running an open-source, reproducibly built, immutable workload image — and any relying party can verify that claim cryptographically without trusting the operator.

Three parties participate. The vendor (data owner) trusts AMD/Intel and NVIDIA silicon, the published workload image they can rebuild from source to the same digest, and standard cryptography — never the operator. The operator (you) runs the control plane but is architecturally excluded from payloads: Confidential Space's hardened image provides no SSH, no serial console, and no interactive access, and memory is encrypted against the hypervisor and Google itself. The relying party (the vendor's prospective customer) trusts the signed shareable report because its signing key is only ever released to the attested workload, and every signature is anchored in a public transparency log.

Design invariant

No component outside the dashed blue boundary in any diagram below ever holds vendor plaintext, a plaintext data-encryption key, or the artifact-signing key. The control plane schedules ciphertext; it cannot read it.

02

Platform & model selection — October 2026 update

Since Rev A, three things moved: NVIDIA shipped Blackwell confidential computing with encrypted NVLink and announced rack-scale TEEs on Vera Rubin; AMD advanced trusted device I/O on its next EPYC generation; and the open-weight frontier turned over almost completely. The trust architecture in sections 03–09 is unchanged — it was designed to be hardware- and model-agnostic. What changes is where it runs and which model it measures.

What changed in the silicon

NVIDIA Hopper (production baseline). Hopper confidential computing is GA in two modes: one GPU passed through per confidential VM, or Protected PCIe (PPCIe), which places all eight GPUs of an HGX H100/H200 board in one CVM. The catch with PPCIe is that GPU-to-GPU traffic over NVLink/NVSwitch is not encrypted in that mode — the board is inside the trust boundary but the fabric is not cryptographically protected. On GCP, Confidential Space support for Hopper GPUs is now GA, which is what this design ships on first.

NVIDIA Blackwell (the target platform). Blackwell closes Hopper's gaps. HGX B200, HGX B300, and RTX PRO 6000 all support confidential computing, with NVLink encryption across up to eight GPUs. Blackwell also supports TDISP and IDE, so the GPU talks to the confidential VM with inline encryption instead of the software bounce buffers Hopper needs — and instead of all-or-nothing PPCIe, a confidential VM can be assigned 1, 2, 4, or 8 GPUs. Independent benchmarking on B200 with Intel TDX measured roughly 1–3% throughput overhead for confidential inference when correctly configured. On GCP, Confidential G4 VMs (RTX PRO 6000 Blackwell on AMD Turin with SEV) are in preview across all G4 regions; confidential A4 (HGX B200) has not been announced, though neoclouds are already running verified confidential HGX B200 in production.

NVIDIA Vera Rubin (roadmap, not for this workload yet). Vera Rubin NVL72 is the first rack-scale TEE: 72 GPUs, 36 Vera CPUs, and the whole NVLink fabric in one encrypted security domain, shipping through partners in the second half of 2026. Azure is among the clouds named as adopting it; GCP is not yet. It's built for trillion-parameter training and serving — well beyond what a per-job scanning enclave needs.

AMD. On the CPU side, EPYC 9005 (Turin) introduced Trusted I/O via TDISP, and in September 2026 AMD posted Linux patches enabling SEV-TIO TDISP on PCIe 6.0 for EPYC 9006 (Venice), alongside Enhanced SMT Protection for SEV-SNP guests. That is the AMD half of the bounce-buffer-free CPU↔GPU path. Two cautions: the RMPocalypse vulnerability (CVE-2025-0033) broke SEV-SNP integrity guarantees on Zen 3 through Zen 5 via the Reverse Map Table initialization, and GCP warned that SEV-SNP Confidential VMs may see longer boot times and performance changes from August 2026 due to a guest kernel migration and security updates. On the accelerator side, AMD's Helios rack emphasizes open interconnect standards rather than an integrated GPU TEE, so AMD Instinct is not yet a fit for this design.

Rev A recommended Qwen3-Coder 480B. It has been overtaken: its SWE-bench Pro score of 38.7% now trails the leaders by more than twenty points. 03

System architecture

Four zones. The vendor zone runs client-side and never uploads plaintext. The control plane orchestrates jobs but handles ciphertext only. The Confidential Space TEE is the sole location where plaintext ever exists. The trust-services layer holds keys, attestation, and transparency infrastructure that binds the other three together.

04

End-to-end workflow

Two phases. Onboarding happens once per workload release and once per vendor; it establishes what "trusted image" means before any data moves. The per-job flow then runs fully unattended — one single-tenant Confidential VM per scan, born for the job and destroyed with it.

Why key release is the linchpin

The KMS key that unwraps vendor DEKs carries an IAM binding whose principal is the Confidential Space workload identity pool, with attribute conditions on the EAT claims: container image digest equals the published value, hardware model is a confidential SKU, GPU CC mode is active, and the debug/monitoring flags are false. Change one byte of the workload image and the digest changes, the condition fails, and no key is ever released. This converts "trust our operations" into "verify our binary."

05

Inside the enclave — processing pipeline

Deterministic tools make the claims; the model makes the judgments. Every CVE in the output traces to a scanner and a pinned database version recorded in the SBOM. The LLM consumes structured scanner output plus source context, and its contributions — triage, exploitability reasoning, OWASP and MITRE mappings, narrative — are labeled as analysis. It cannot invent a CVE ID into the findings set because findings are scanner-owned fields.

06

Output artifacts & provenance chain

Each job emits three signed documents, and one provenance statement binds them to the inputs and the exact workload that produced them. The signing key lives in Cloud KMS behind the same attestation condition as the decryption key — so a valid signature is itself evidence that the audited, unmodified pipeline ran.

Redaction as architecture, not behavior

The shareable report's renderer receives only the aggregated findings table — category, technique ID, severity, count. It has no access to file paths, snippets, or remediation text. Leakage into the public tier is therefore impossible by construction, which is exactly the argument the vendor's counsel and the relying party's security reviewers will want to hear.

09

Operational notes & residual risks

Scaling and tenancy

Isolation is per-job, not per-cluster: each scan gets a fresh Confidential VM from a managed instance group template, which eliminates cross-tenant residue and makes the plaintext lifetime equal to the job duration. Cold start (VM boot, attestation round-trip, weight load into VRAM) runs a few minutes; amortize it for large customers with a warm pool of attested-but-idle VMs that have not yet requested any key — a warm VM holds nothing sensitive until step 7 of Fig. 3. Model footprint follows the phases in section 02: a single-GPU dense coder in Phase 1, then Nemotron 3 Ultra at NVFP4 (roughly 275 GB of weights) on a 4–8 GPU Blackwell confidential VM. Keep the same vLLM serving interface across phases so a model swap is a new image digest and AIBOM, not a pipeline change.

Updates without breaking trust

Every workload release is a new image digest, which means every release invalidates the old KMS conditions by default — that is a feature. Publish new measurements, the reproducible-build recipe, and the diff-scoped audit note to Rekor; give vendors a pinning window during which both digests are accepted so their key policies roll forward on their schedule, not yours. Scanner vulnerability databases update on the same rhythm as image releases so that DB contents stay part of the measured, attested TCB.

What this design does not defend against

Honesty here strengthens the sales conversation. The TCB still includes AMD/Intel and NVIDIA silicon and microcode — a hardware vulnerability (and SEV-SNP/TDX errata do occur) is a shared fate with every confidential-computing customer; subscribe to the GCP security bulletins and rotate measurements after firmware fixes. A malicious workload you publish would be attested faithfully — attestation proves identity, not virtue — which is why the third-party audit of the open, reproducible image is a load-bearing part of the product rather than a marketing extra. And side channels within shared hardware remain a research-grade risk; single-tenant-per-job VMs and no-external-egress narrow it substantially but do not make it zero.

Track CPU TEE advisories as product events. RMPocalypse (CVE-2025-0033) showed SEV-SNP integrity can fail at the Reverse Map Table on Zen 3–5, and GCP's August 2026 SEV-SNP guest kernel migration changed boot behavior. Encode the minimum patched firmware/TCB version as a KMS key-release condition, so an unpatched host simply cannot obtain keys — this is also why Phase 1 prefers Intel TDX on A3, with Intel Trust Authority as the independent verifier.

Open-source project — Confidential Assurance Framework

Rev C publishes the whole system as an Apache-2.0 project. That is not a distribution decision bolted on afterwards: it completes the trust model. Until now, a vendor had to trust an audit report that the measured image was benign. Open source lets them rebuild the image from source, get the same digest, and know that this digest is the only one KMS will release keys to.

Vendor-key mode: the strongest form of "their keys"

The original requirement was that vendors encrypt with their own keys. Open source makes a stronger option practical. A vendor creates a Cloud KMS key in their own project and grants decrypt only to the principalSet for the published image digest. The vendor then owns the key-release policy outright: they can refuse a new release until they have rebuilt and reviewed it, and revoke access at any time, whatever the operator does.

Governance and release discipline

Contributions use DCO sign-off (no CLA). Changes to workload/, wip.tf, the event schema or the shareable template need two trust-boundary reviewers. Every tagged release is built twice on separate runners and fails if the digests differ; it is signed keylessly with cosign, carries SLSA build provenance, and publishes the digest and attestation policy. Hosted operators give 14 days' notice before adopting a new digest so vendors in vendor-key mode can review it first. The project aims for a neutral foundation home (Confidential Computing Consortium or OpenSSF) once maintainers come from three or more organizations.

What open-sourcing does not change

Confidentiality never depended on secrecy of the code, so nothing weakens. Two things are newly exposed and accepted: adversarial vendors can study the rules to evade them (the service attests to what was found, not to what a determined vendor could hide), and anyone can run a competing deployment. That second point is the intended outcome for a trust primitive.
